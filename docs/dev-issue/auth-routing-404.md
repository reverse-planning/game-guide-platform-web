## 문제 (현상 / 영향)

- 배포 환경에서 특정 페이지를 새로고침하거나 URL로 직접 접근할 경우 **404가 발생**하여 서비스 진입이 차단되는 문제가 있었다.
- 로그인 이후 일부 흐름에서 **네트워크 오류**가 발생했으며, `next` 파라미터 처리 과정에서 **리디렉션이 반복**되는 케이스가 확인되었다.

## 원인 분석

### 1. 호스팅 레벨 라우팅 미스매치

SPA는 어떤 경로로 접근하더라도 `index.html`을 먼저 내려받아야 한다.  
그러나 Vercel이 `/guides` 등의 경로를 정적 파일로 해석하면서, 딥링크 및 새로고침 시 **404를 반환**하고 있었다.

### 2. 세션 확인 로직의 미구현 API 의존

초기 설계에서 세션 유효성 확인을 위해 `GET /api/session` 호출을 사용하고 있었다.  
해당 API가 미구현 상태였기 때문에 배포 환경에서 **네트워크 오류(AppError: NETWORK)** 가 발생했다.

### 3. 책임 경계 붕괴로 인한 리디렉션 루프

다음 책임이 여러 레이어에 분산되어 있었다.

- 세션 초기화
- 에러 변환
- 라우팅 리디렉션

그 결과 `next` 기반 리디렉션이 중복 실행되며 **무한 리디렉션 루프**가 발생했다.

## 해결 전략

### ✅ SPA fallback rewrite 적용

Vercel 설정에 SPA fallback을 추가하여, 딥링크 및 새로고침 시에도 항상 `index.html`이 제공되도록 수정했다.

```json
{
  "rewrites": [
    {
      "source": "/api/:path*",
      "destination": "https://api.doi2.my/api/:path*"
    },
    {
      "source": "/(.*)",
      "destination": "/"
    }
  ]
}
```

### ✅ 세션 확인 로직 단순화

- 미구현된 /api/session 의존 제거

- 라우터 loader는 스토어의 인증 상태를 읽기 전용으로 판단하도록 변경

이를 통해 불필요한 네트워크 오류를 제거했다.

### ✅ 책임 분리 재정립

레이어별 역할을 다음과 같이 명확히 분리했다.

- 인터셉터
  - 401 감지 시 세션 초기화
  - 표준 에러(AppError)로 변환
  - ❌ 라우팅 관여하지 않음

- 라우터 / 화면
  - 인증 가드 처리
  - next 기반 리디렉션 정책 단일화

## 결과

- /guides, /guides/:id 딥링크 및 새로고침 시 404 문제 해결
- 로그인 이후 발생하던 네트워크 오류 제거
- next 기반 리디렉션 루프 제거
- 인증 및 라우팅 정책을 단일 위치로 고정하여 추후 기능 확장 시 재발 가능성 최소화

## 회고

SPA 환경에서는 **호스팅 라우팅, 클라이언트 라우터, 네트워크 계층**의 책임 경계를 명확히 나누는 것이 안정적인 인증 흐름을 만드는 핵심이다는 것을 알게 되었다.
